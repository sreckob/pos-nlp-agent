## 1. Project Description and Current Status

### 1.1 What it is

**POS NLP Agent** is a conversational AI system that allows non-technical users —
cardholders, merchants, dispute analysts, and loyalty members — to query a POS payment
transactions database using natural language in Serbian or English. Users interact with
a chat interface; the system generates and executes PostgreSQL SELECT queries behind
the scenes, returning human-readable answers with structured result tables.

**Who the user is:** bank or payment processor staff and cardholders who need quick
answers from transaction data without knowing SQL or navigating complex BI dashboards.
A cardholder can ask *"Why was my card declined yesterday?"*; a merchant can ask
*"Export my declined transactions this month to Excel"*; a cardholder can report a
double charge and receive a reversal through an approval workflow.

**Value proposition:** natural language access to structured payment data with
role-appropriate scoping, bilingual support (Serbian/English), and a split-of-duties
approval workflow that mirrors real banking operations.

### 1.2 Current status (as of 2026-05-14)

- **Fully deployed in production.** Backend on Railway, frontend on Vercel with
  automatic CI/CD on push to `main`.
- **Four-path conversational agent** is live and tested end-to-end for all paths.
- **Split-of-duties ops console** is implemented and deployed — customers submit
  dispute/loyalty requests; operations staff review via a split-screen dashboard,
  approver agent auto-generates audit recommendations, approved actions update the DB.
- **Security hardening completed:** credentials rotated, git history purged of leaked
  files, connection pooling, parameterised queries, ops endpoint authentication.
- **Multi-LLM abstraction** implemented via LiteLLM — provider (Claude/Gemini/Mistral)
  is configurable via a single env var without code changes.
- **Automated validation suite** running: 56 test cases, temperature sweep completed.

**Out of current scope:** user authentication (single-tenant demo), Redis-backed
session state (single Railway dyno acceptable for demo), vector RAG for the approver
agent (designed, not yet implemented — see §6).

## 2. Data

### 2.1 Sources

| Source | What is used | Access |
|---|---|---|
| Supabase PostgreSQL | Primary data store: all transaction history, loyalty accounts, ops queue | Direct psycopg2 connection via `DATABASE_URL` |
| Synthetic transaction generator (`db/supabase/seed_v2.py`) | 100,000 realistic POS transactions seeded at project start | One-time seed script |
| Daily top-up (`db/supabase/topup.py`) | Adds recent transactions to keep data "live" | Scheduled manually before tests/demos |
| Demo seed (`db/supabase/demo_seed.py`) | 3 dispute duplicate pairs + 2 loyalty gap scenarios + recent normal transactions | Run before demos and test suites |
| Receipt images (`receipts/`) | 3 PNG receipt images for Vision OCR testing in the dispute path | Generated by `db/supabase/generate_receipts.py` |

### 2.2 Volume and storage format

| Table | Rows | Format | Purpose |
|---|---|---|---|
| `transactions` | 105,525 | PostgreSQL, 22 columns | Core query target for all four paths |
| `loyalty_accounts` | 4 | PostgreSQL, 7 columns | Loyalty tier, points balance, PAN mapping |
| `pending_approvals` | Variable | PostgreSQL + JSONB payload | Ops approval queue for dispute/loyalty requests |

**Key transaction columns:** `transaction_id` (UUID), `pan_masked`, `amount`, `currency`,
`status` (APPROVED/DECLINED/REVERSED/PENDING), `response_code` (ISO 8583), `card_brand`,
`card_type`, `merchant_name`, `merchant_category`, `dispute_status`, `loyalty_points_earned`,
`loyalty_points_credited`.

### 2.3 Preprocessing

There is no text chunking — the data is fully structured and stored in a relational
database. The deliberate architectural choice is **NL2SQL rather than RAG** for the
transactional query paths:

- The full database schema (~400 tokens) fits in the LLM context window as a system
  prompt; no vector index is needed.
- SQL is more precise than semantic search for structured tabular data — it supports
  exact filters, aggregations, and joins that would be unreliable via embedding similarity.
- The LLM generates PostgreSQL `SELECT` statements; psycopg2 executes them; a
  read-only guard blocks any DML/DDL before execution.

The only "preprocessing" is the masking of card numbers in the source data
(`pan_masked` format: `411111******4242`) to comply with PCI-DSS safe-handling
requirements — no actual card data reaches the Anthropic API.

### 2.4 Demo data lifecycle

```
seed_v2.py (once)     → 100,000 baseline transactions
topup.py (daily)      → appends recent-dated transactions
demo_seed.py (before demo/tests)
    → 3 dispute duplicate pairs (Maxi/4242, NIS Petrol/5555, Gigatron/1111)
    → 2 loyalty gap scenarios (Visa/4242, Mastercard/5555)
    → recent normal transactions for all demo PANs
```

## 3. Pipeline Architecture

### 3.1 Overview

```
Browser (React 18 — Vercel)
    ↕ WebSocket  /ws/{session_id}
    ↕ REST       /dispute/submit  /loyalty/submit  /ops/*
FastAPI backend (Railway)
    → LangGraph INVESTIGATOR AGENT
        → Router node (runs every turn)
              Classifies role + language
              Hybrid: user selects role + AI validates each message
              3-strike mismatch guard → suggests or forces channel switch
        → Four specialist paths (SELECT only, never write):
              CARDHOLDER — own transactions filtered by PAN
              MERCHANT   — terminal/revenue data + Excel export
              DISPUTE    — duplicate detection + Vision OCR for receipts
              LOYALTY    — uncredited points gap detection
        → SQL validator (read-only guard, regex blocklist)
        → SQL executor (psycopg2 + connection pool)
        → Response formatter (enforces flag consistency from DB results)
    → pending_approvals queue ← customer Submit enqueues here
    → APPROVER AGENT (approval_agent.py)
          Runs when ops user opens a pending item
          Hard pre-checks (PAN/amount/merchant match, sum verification)
          LLM audit decision: APPROVE | REJECT + confidence + audit_summary
    → write_ops.py ← called ONLY after ops APPROVE via /ops/decide
          approve_dispute_reversal() — marks duplicate as REVERSED
          credit_loyalty_points()   — updates loyalty_accounts atomically
    → WebSocket push → customer chat notified of ops decision
PostgreSQL on Supabase
    → transactions (105,525 rows)
    → loyalty_accounts (4 demo members)
    → pending_approvals (ops approval queue)
```

### 3.2 Key design decisions

**LangGraph state machine over plain Python.** Multi-turn context (last 20 messages,
`last_sql`, `last_rows`, role, language, mismatch count) flows through a typed
`AgentState` dict. Conditional edges handle routing cleanly without nested if/else.

**Hybrid router.** The user selects a role at login (reduces cognitive load); the
router LLM validates every subsequent message against the selected channel. A 3-strike
mismatch policy suggests switching at strikes 1–2 and forces a reset at strike 3,
preventing information leakage between roles.

**NL2SQL not RAG.** Structured tabular data is more precisely served by SQL than
semantic vector search. No vector database needed — schema fits in the context window.

**Separation of duties.** Investigator agents are strictly read-only (SQL validator
enforces this). Write operations only execute after a human operations decision
(`POST /ops/decide`), gated by an approver LLM that independently verifies the
evidence. This mirrors real banking "four-eyes" compliance requirements.

**Multi-LLM abstraction.** A LiteLLM wrapper (`llm_client.py`) allows the entire
text-path to switch between Claude, Gemini, and Mistral by changing a single
`LLM_MODEL` env var. The Vision path (dispute receipt OCR) stays on Claude by default
as it has the strongest multimodal document understanding.

**Per-node temperature control.** Six independent temperature env vars
(`TEMP_ROUTER`, `TEMP_CARDHOLDER`, etc.) allow fine-grained tuning. Defaults are
informed by an automated sweep (see §5).

### 3.4 API endpoints

| Endpoint | Type | Purpose |
|---|---|---|

## 4. Evaluation Approach

### 4.1 Validation set

56 hand-crafted test cases across 12 categories, stored in `validation/test_cases.json`.

| Category | Count | What it tests |
|---|---|---|
| `exact_match` | 5 | Approval code / terminal / PAN lookups |
| `range_query` | 6 | Amount and date range filters |
| `status_filter` | 5 | DECLINED/APPROVED combined filters |
| `aggregation` | 6 | COUNT, SUM, GROUP BY queries |
| `multi_filter` | 5 | Complex combined filters |
| `multi_turn` | 3 | Multi-step refinement context retention |
| `edge_case` | 7 | No results, blocked DML, off-topic queries |
| `cardholder` | 4 | PAN isolation, declined filter, bilingual |
| `merchant` | 4 | Name filter, aggregate, Excel export flag |
| `dispute` | 4 | Duplicate detection EN + SR, false positive |
| `loyalty` | 4 | Enrolled check, missing points EN + SR, non-enrolled |
| `router` | 3 | Mismatch suggest, correct-channel stay |

Each test specifies: `prompt`, `router_current_channel` (channel context for priming),
`expected_sql_contains` (list of required keywords), `expected_result` (pass criteria).

### 4.2 Metrics

| Metric | Definition | What it captures |
|---|---|---|
| **SQL accuracy** | % of tests where generated SQL contains all expected keywords | Correctness of query construction |
| **Result accuracy** | % of tests where response meets `expected_result` criteria | End-to-end correctness (rows, flags, blocking) |
| **Overall accuracy** | Both SQL and result accuracy pass | Combined single-turn pass rate |
| **SQL consistency** | % of tests producing identical SQL across N repeated runs at same temperature | Model variance / reliability |

Path-specific `expected_result` values include: `has_results`, `no_results`,
`zero_or_more`, `blocked`, `clarification`, `dispute_found`, `no_dispute`, `enrolled`,
`not_enrolled`, `credit_recommended`, `suggest_switch`.

### 4.3 Test infrastructure

- `validation/run_tests.py` — WebSocket-based automated runner. Seeds DB before run
  (`--seed`), supports category filtering (`--category`), labels runs by temperature
  (`--temperature`) for sweep comparison, saves JSON reports (`--output`).
- `validation/tune_temperature.py` — automated temperature sweep. Starts/stops fresh
  uvicorn subprocesses per setting, runs N repeated trials, measures mean accuracy and
  SQL consistency, prints a comparison table and recommendation.
- `validation/UI_TEST_PLAN.md` — 30 manual UI test scenarios with copy-paste prompts,
  expected behaviour, and pass/fail criteria for all four paths plus router and safety.

### 4.4 Important distinction: first-shot vs conversational accuracy

The automated test suite measures **first-shot accuracy** — whether the correct
response is produced on the very first message. However, the system is architected as a
**multi-turn conversational agent**: when context is missing (no card number, no
merchant ID, ambiguous date), the agent correctly asks for clarification and succeeds
on the next turn. First-shot accuracy therefore underestimates the real-world task
completion rate. Many test "failures" are the system doing the right thing: asking
*"Please provide your card's last 4 digits"* before querying.

## 5. Preliminary Results

### 5.1 Temperature sweep — Claude claude-sonnet-4-6

An automated sweep across four temperature settings was run using
`validation/tune_temperature.py`. Each setting was tested in 3 independent runs (each
run = full 56-test suite); mean accuracy and SQL consistency are reported.

| Setting | Specialist temp | Router/Approver temp | Mean accuracy | SQL consistency | Accuracy range |
|---|---|---|---|---|---|
| baseline | 0.0 | 0.0 | 39.3% | 64.3% | 33.9–42.9% |
| low | 0.1 | 0.0 | 42.3% | 67.9% | 41.1–44.6% |
| **medium** ★ | **0.3** | **0.0** | **44.6%** | **75.0%** | 42.9–46.4% |
| high | 0.5 | 0.0 | 25.6% | 57.1% | 5.4–39.3% |

★ **Recommended setting: specialist temperature 0.3.**

**Key findings:**
- Medium (0.3) wins on both accuracy AND consistency simultaneously — counterintuitive
  but interpretable: Claude at 0.0 is too rigid for NL2SQL, small variance at 0.3 helps
  explore better SQL phrasings.
- High (0.5) is catastrophically unstable — one run scored 5.4% (all API calls failing
  at peak load), showing that 0.5 is above the reliable operating threshold.
- Router and approver nodes are kept at 0.0 — classification and binary decisions
  should be deterministic.

### 5.2 Path-specific accuracy (at temperature 0.3)

| Category | Pass rate | Notes |
|---|---|---|
| `cardholder` | 4/4 — **100%** | Prompts include card context upfront |
| `router` | 3/3 — **100%** | Mismatch detection reliable |
| `dispute` | 2/4 — **50%** | Requires exact seeded duplicate pairs |
| `loyalty` | 1/4 — **25%** | PAN propagation sensitivity |
| `edge_case` (blocked) | 4/7 — **57%** | DML blocking correct; ambiguous queries vary |
